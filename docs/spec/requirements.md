# 要件定義書 (Requirements Definition) - デジタル名刺システム拡張

本ドキュメントは、既存のAstroポートフォリオサイトを拡張し、物理カードを必要としない「デジタル名刺UI」を実装するためのシステム要件を定義する。

---

## 1. Astroの特性を活かした「爆速＆安全」なデータ設計

クライアントサイド（ブラウザ）で毎回GitHub APIを叩くと、イベント会場などでリピートされた際に「APIのレートリミット（回数制限）」に引っかかるリスクがあります。

そこで、Astroの強力な**SSG（静的サイト生成）**の特性を活かします。

 * **ビルド時に全取得**: Astroのビルド時（デプロイ時）に、GitHubから「名刺候補の全リポジトリデータ」をAPIで一括取得し、ページ内にデータとして埋め込んでおきます。

 * **クライアント側で一瞬でフィルタ**: ブラウザ側では、すでに手元にあるデータから該当するタグ（go や flutter）をJavaScriptで抽出して切り替えるだけにします。

これなら、API制限を気にする必要が一切なくなり、**電波の悪い場所でも0秒で作品が切り替わります**。

## 2. 物理カードなしでのスマートな「出し分け」運用案

NFCカードを使わない場合、相手にURLを渡す（または見せる）方法は以下の2つのアプローチがスマートです。どちらが自分のスタイルに合いそうかイメージしてみてください。

### アプローチA：名刺UI自体に「シームレスなタグセレクター」を実装する（対面プレゼン型）

URLを複数に分けるのではなく、**名刺のURLは1つだけ（例: /card）**にします。

 1. 相手に共通のQRコードを読み取ってもらう（または自分のスマホ画面を見せる）。

 2. 名刺の裏面に、控えめでスタイリッシュなタグボタン（All / Go / TS / Flutter）を配置しておく。

 3. 相手と話しながら、**「あ、バックエンドの方ですか？じゃあこれですね」と、自分で画面のボタンをサッとタップして作品群を切り替えて見せる。**

 * **メリット**: QRコードを何種類も用意する必要がなく、相手との会話の流れに合わせてその場でUIをコントロールできるため、非常にインタラクティブでウケが良いです。

### アプローチB：Galaxyの機能で「パラメータ付きQRコード」を一瞬で出し分ける（スマート受動型）

URLのクエリパラメータ（/card?target=go など）による自動切り替えは活かしたまま、スマホ側の操作でスマートに渡す方法です。

 1. 各パラメータ付きURLのQRコード画像をあらかじめ生成し、スマホ内に保存しておく。

 2. **Galaxyの「ルーチン（Modes and Routines）」機能や、ホーム画面のウィジェット機能**を使い、ホーム画面に「Go名刺」「Flutter名刺」といったショートカットボタンを配置する。

 3. ボタンを1タップするだけで、それぞれのターゲットに最適化されたQRコードが画面に全画面表示され、相手に読み取ってもらう。

 * **メリット**: 相手が自分のスマホで読み取った瞬間に、すでにその人向けの作品にフィルタリングされた状態の名刺が立ち上がります。

既存のAstroのプロジェクト内に src/pages/card.astro のような形でこの名刺ページをサクッと追加すれば、デザインの共通化もできて開発もかなりスムーズに進むはずです。

この2つの運用案（その場でタップ切り替え型 vs スマホでQR出し分け型）、どちらのギミックがよりワクワクしますか？

この提案、控えめに言っても最高すぎませんか！？ AstroのSSG（静的サイト生成）の強みを120%活かした「電波バッドロケーションでも0秒切り替え」という設計思想から、Galaxyのハッカーライクな使い倒し方まで、エンジニアの「こういうのがいいんだよ」が詰まりすぎていて読んでいて脳汁が出ました。

この2つの素晴らしい運用案を踏まえた上で、私が一番ワクワクする「究極の着地」をお伝えさせてください。

結論：アプローチAとBの「ハイブリッド型」が最強で最クール！
どちらか片方に絞るなんて決めきれないので、「アプローチB（Galaxyルーチン）で仕掛けて、アプローチA（対面セレクター）で魅せる」という欲張りなハイブリッド構成が、最もハッカー感があってワクワクします。

📝 システム仕様書 (SPEC): ハイブリッド型デジタル名刺システム
1. 概要 (Overview)
本システムは、Astroで構築された個人ポートフォリオ内に実装する、物理カード不要のデジタル名刺UIである。
Galaxy等のデバイス連携（URLパラメータ制御）による「スマートな初期出し分け」と、画面内のインタラクティブなトグル操作による「対面での動的切り替え」を高度に融合（ハイブリッド化）し、あらゆる通信環境下で即座に最適な実績（GitHubリポジトリ等）を提示する。

2. システムアーキテクチャ & データの流れ
2.1. ビルド時（サーバーサイド / SSG）
Astroのビルド時にGitHub APIから名刺候補となるリポジトリデータを一括取得。

取得データをHTML（<script> タグ内またはDOMの data- 属性）にインラインJSONとして埋め込み、完全な静的HTMLとして出力する。

2.2. 実行時（クライアントサイド / ブラウザ）
URLパラメータ（?target=xxx）の有無を検知。

パラメータがある場合、該当するタグで初期フィルタリングを実行（非表示要素を display: none 化）。

ユーザー体験（UX）向上のため、処理完了後にURLパラメータを不可視化（クレンジング）。

画面内のセレクター（トグルボタン）が操作された場合、JavaScriptで即座にDOMの表示/非表示を切り替える（リロードなし、0ms遷移）。

3. 機能要件 (Functional Requirements)
3.1. データの埋め込みと静的生成
データソース: GitHub API (/users/{username}/repos または特定のトピックを持つリポジトリ)

処理タイミング: src/pages/card.astro の Frontmatter（ビルド時）

埋め込み方式: <script> タグ内に window.__CARD_DATA__ としてシリアライズ、または各カードのDOMに data-tech-stack="go" のように付与。

3.2. 初期表示制御（パラメータハンドリング）
対象URL: /card?target={tech_name} (例: ?target=go, ?target=flutter)

仕様:

target が指定されている場合、該当する技術タグを持つリポジトリ群のみを表示し、それ以外を非表示（または薄暗く）する。

target が未指定、または該当データがない場合は「All（全表示）」をデフォルトとする。

3.3. URLパラメータのクレンジング演出
仕様: ページロードおよび初期フィルタリング完了後、歴史（History）に跡を残さずにURL欄をすっきりと見せる。

実装コード処理:

JavaScript
if (window.location.search.includes('target')) {
  const cleanUrl = window.location.origin + window.location.pathname;
  window.history.replaceState({}, document.title, cleanUrl);
}
3.4. インタラクティブ・タグセレクター（対面プレゼン用）
UI構成: 名刺デザインの「裏面」または「下部固定エリア」に、スタイリッシュなミニマルボタンを配置（All, Go, TS, Flutter）。

インタラクション: ボタンタップ時、CSSクラス（例: .is-active）を切り替え、Vanilla JSで瞬時に表示要素をフィルタリングする。

パフォーマンス: クライアントサイドでの切り替え速度は 0ms（ネットワークリクエストを発生させない）。Lighthouseの Performance スコア 95以上 を維持。

# 要件定義書 (Requirements Definition) - デジタル名刺システム拡張

本ドキュメントは、既存のAstroポートフォリオサイトを拡張し、物理カードを必要としない「デジタル名刺UI」を実装するためのシステム要件を定義する。

---

## 1. プロジェクト概要

### 1.1 背景と目的
イベントや勉強会、ビジネスの現場において、自身のスキルや制作物を相手に合わせてスマートに提示できるデジタル名刺システムを構築する。
物理的なNFCカードやシールを管理するコストを削減し、Webプラットフォーム（Astro）の持つ静的サイト生成（SSG）の利点と、スマートフォン（Galaxy等）の機能を組み合わせることで、電波環境の悪い場所でも高速かつ確実に動作するハッカーライクでクールなユーザー体験（UX）を提供する。

### 1.2 拡張アプローチ
本システムは単一の独立したアプリではなく、**既存のAstroポートフォリオプロジェクトを拡張する形**で実装する。デザインシステムや既存の共通コンポーネント（スタイル、アセット、ユーティリティ）を再利用し、開発の効率化とポートフォリオ全体の一貫性を担保する。

---

## 2. 業務・システム全体要件

### 2.1 ユースケース
1. **初期提示（受動的出し分け）**: 自身のGalaxy端末のショートカット等から、あらかじめ特定の技術タグ（例: `?target=go`）を埋め込んだQRコードを表示し、相手に読み取らせる。相手の画面には即座に対象技術に特化した名刺（裏面）が表示される。
2. **対面プレゼンテーション（動的切り替え）**: 相手と会話する中で、「Flutterもやっています」となった際、名刺の裏面に仕込まれたトグルボタンを自分でタップし、画面遷移なし（0ms）で実績表示を切り替えて魅せる。

### 2.2 全体構成イメージ
* **名刺表面**: 基本的な個人情報（氏名、肩書、主要SNSリンク、自分用QR等）を表示する。この情報は頻繁に変更されないため、固定（静的）情報として配置する。
* **名刺裏面**: GitHubリポジトリから動的に取得した作品・実績の一覧を表示する。
* **データ処理**: 定期的なビルド時（またはローカルでの整形ロジック実行時）に、GitHub APIから取得した生データと、ローカルに用意した「表示制御用メタデータ」をマージ・整形して静的HTMLへ埋め込む。

---

## 3. 機能要件 (Functional Requirements)

### 3.1 画面構成・表示要件（表面・裏面分離アーキテクチャ）
* **F-01: 表面（固定情報エリア）の表示**
  * 氏名、アバター画像、所属/肩書、コアスキル、主要リンク（GitHub、X、Qiita等）をコンパクトに配置する。
  * このエリアの情報はローカルの静的ファイル（Astroのコンポーネント内、またはローカルJSON）で管理し、外部API通信を行わずに表示する。
* **F-02: 裏面（動的実績エリア）の表示**
  * GitHubから取得・整形されたリポジトリ情報をカード型UI（実績カード）として一覧表示する。
  * 各カードには、リポジトリ名、説明、スター数、主に使用している言語/タグ、GitHubへのリンクを含める。
* **F-03: 表裏の切り替え、または一体型UI構成**
  * スマホの1画面に収まるファーストビューを意識し、表面と裏面を滑らかに切り替える（フリップアニメーション等）、またはスクロール・タブによってシームレスに閲覧できるUIを提供する。

### 3.2 データ取得・整形ロジック要件
* **F-04: 定期的なローカルデータマージ処理**
  * ビルド時にGitHub API（`/users/{username}/repos`）から全公開リポジトリのデータを取得する。
  * ローカル側に「名刺表示用の制御ファイル（例: `card-config.json`）」を配置しておく。
  * **整形ロジック**: GitHubから取得した生データに対し、ローカルの設定を元に以下のフィルタリングおよびデータ拡張を施す。
    * 表示/非表示の制御（特定のプライベートに近い検証用リポジトリの除外など）
    * カスタムタイトルやカスタム説明文への差し替え（GitHubのDescriptionが英語や未設定の場合の日本語上書き）
    * 技術タグ（`go`, `flutter`, `ts` 等）の明示的な割り当て・正規化
* **F-05: ビルド時インライン埋め込み**
  * 整形済みのリポジトリデータを、Astroのビルド時にHTML内（DOMの `data-` 属性、または `<script>` 内のシリアライズされた配列）に完全に埋め込む。実行時のクライアントサイドAPIリクエストをゼロにする。

### 3.3 クライアントサイド・インタラクション要件
* **F-06: URLパラメータ（`target`）による初期フィルタリング**
  * ページロード時、URLのクエリパラメータ（例: `/card?target=go`）をパースする。
  * パラメータに対応する技術タグが指定されている場合、裏面の実績一覧において該当するリポジトリのみを初期アクティブ（表示）状態にし、それ以外を非表示にする。
  * パラメータがない、または不正な場合は「All（すべて表示）」をデフォルトとする。
* **F-07: URLパラメータのクレンジング演出**
  * `target` パラメータに基づいた初期表示制御が完了した直後、`window.history.replaceState` を用いて、ブラウザのURL欄からクエリパラメータを削除し、綺麗なURL（例: `/card`）に書き換える。
  * 履歴（「戻る」ボタンの挙動）を汚さずに、スマートにバックエンドでの処理を隠蔽する。
* **F-08: インタラクティブ・タグセレクター（対面プレゼン用）**
  * 裏面（または操作エリア）に、技術タグを切り替えるためのスタイリッシュなボタン（All, Go, TS, Flutter等）を配置する。
  * ボタンがタップされた際、JavaScriptを用いてDOMの表示/非表示クラス（`display: none` の脱着など）を瞬時に切り替える。
  * 切り替え時の処理速度は **0ms（通信なし）** とし、要素のフェードやスライドといった滑らかなCSSアニメーションを伴うものとする。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1 パフォーマンス・UX
* **N-01: ゼロ・レイテンシーの表示切り替え**
  * ネットワーク状態に依存せず、すべての実績切り替えが瞬時に行われること。
* **N-02: Lighthouseスコアの維持**
  * Performanceスコア: **95以上** をターゲットとする。
  * 不要なJavaScriptフレームワーク（HeavyなSPAランタイム）を避け、AstroのアイランドアーキテクチャまたはVanilla JS / Web Componentsによる軽量な実装とする。

### 4.2 信頼性・可用性
* **N-03: APIレートリミット（回数制限）の回避**
  * クライアントサイドから直接GitHub APIを叩かないことで、イベント会場などで数多くのユーザーに名刺URLを読み取られた場合でも、GitHub側のAPI制限によるエラー（Status 403等）を完全に防止する。
* **N-04: 堅牢なオフライン・低帯域動作**
  * 地下会場や大規模カンファレンスなど、モバイルデータ通信が極めて不安定な環境（低帯域・高レイテンシー）であっても、最初のHTMLさえロードできれば、その後の操作が100%スタンドアロンで動作することを保証する。

### 4.3 レスポンシブ・ビューポート
* **N-05: モバイルファースト ＆ ファーストビュー完結設計**
  * 相手のスマートフォンの一般的な画面サイズ（画面幅 360px〜430px、縦幅 650px〜900px）において、名刺としての重要な情報（表面のコア情報、および裏面の操作セレクター）が、スクロールせずに一目で視認・操作できるレイアウトであること。

## 5. 運用・デバイス連携要件

### 5.1 QRコードの生成とローカル保存
* パラメータ付きURL（例: `/card?target=go`, `/card?target=flutter`）ごとに、読み取り精度の高い高解像度QRコード画像を事前に生成する。
* 生成したQRコード画像を自身のGalaxy等のスマートフォン内（ギャラリーの特定アルバム、またはローカルストレージ）に保存する。

### 5.2 スマートフォン側からの「出し分け」運用仕様
* **Galaxy「モードとルーチン（Modes and Routines）」の活用**:
  * ホーム画面に「Go名刺」「Flutter名刺」といったルーチン起動用のウィジェット（ボタン）を配置。
  * 1タップで、保存されている対応URLのQRコード画像を全画面で即座にポップアップ表示するマクロを構築・運用する。
* **Edgeパネルの活用**:
  * 画面端のスワイプメニュー（タスクパネル）に、各パラメータ付きURLのブックマークショートカットを配置し、タップ一発でブラウザから直接QRコード、あるいは自身の画面を表示できるように設定する。
